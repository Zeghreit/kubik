# Библиотека материалов: слияние вместо роста (v2.29)

Две жалобы, две несвязанные болезни. Обе — в библиотеке материалов, и работа
над каналами текстур была сознательно отложена, пока они не вылечены.

## 1. Каждый открытый меш плодил материалы

`materialDefSig(d)` — стабильная подпись `{name, color, roughness, metalness,
bevel, masks}` — требовала ТОЧНОГО совпадения. Любая мелочь мимо: цвет,
съехавший на один 8-битный шаг на круге sRGB → linear → sRGB; roughness 0.52
против набранных 0.5; правка, сделанная руками после первого импорта. Промах
оставлял единственную ветку — ЧЕКАНИТЬ: «Skin (imported)», потом
«Skin (imported 2)». Одна запись за открытие, и обратно ничего не сливалось.

**Имя стало идентичностью — только на пути ИМПОРТА.** Индекс `byName`
(имя в нижнем регистре → id) засевается из библиотеки при создании
`importMaterialContext()`. При промахе по подписи то же имя переиспользует
запись, и **побеждает МЕСТНОЕ определение** — материал, который человек
настроил, не должен перекрашиваться тем, что оказалось в файле.

Четыре правила, и три из них существуют потому, что без них что-то ломалось:

- **Источник без имени чеканит свою запись.** `raw` подставляет «Imported», и
  слияние по нему схлопнуло бы все безымянные материалы файла в один, убив их
  цвета. Это противоположность слиянию.
- **ПРЕСЕТЫ НЕ ЦЕЛИ ДЛЯ СЛИЯНИЯ.** Solid, Plastic и Metal несут
  `color: null` — «какой сейчас серый у темы». Слить ЗОЛОТОЙ материал с именем
  «Metal» на пресет Metal значит перекрасить его в серый и заставить следовать
  теме навсегда, а «Metal» — одно из самых частых имён в скачанном ассете.
  Единственная дорога на пресет — прежний themed-preset shortcut, ограниченный
  `nearHex` и допуском по roughness. `_imp_probe`, проверка
  `11.rename_on_collision`, утверждает именно это с a2.69; первая версия v2.29
  её бы сломала.
- **Свежая запись не становится целью для слияния внутри своего же импорта.**
  `byName` засевается один раз и не растёт; для цикла переименования
  используется отдельное множество `taken`. Поэтому два материала в ОДНОМ файле
  с одинаковым именем остаются двумя со своими цветами, а то же имя из
  СЛЕДУЮЩЕГО файла садится на то, что оставил этот.
- **Ключ — имя целиком, и запись помнит его как `srcName`.** Хранимое имя
  режется до 32 символов, поэтому запись, отчеканенная из
  `Metal_Rough_Scratched_Variant_01_Red`, называется
  `Metal_Rough_Scratched_Variant_01`: ключ по срезу склеил бы её с `..._Blue` и
  убил цвет, а ключ по полному имени никогда бы её не нашёл. `srcName` делает
  для имени то же, что `srcSig` — для вида.

**Сборщик в `restoreDoc` по имени НЕ сливает, и это осознанно.**
`serializeDoc` пишет в `doc.materialLib` ВСЮ библиотеку, пресеты в том числе,
под их неизменными именами. Ключ по имени означал бы, что изменённый Metal из
файла всегда находит локальный Metal, `known === d.id`, и определение файла
молча пропадает — ровно тот баг, который описан в комментарии десятком строк
выше сборщика («добавь Metal царапины, сохрани, открой файл где угодно ещё — и
модель приехала в чистом Metal»). Определения проектного файла И ЕСТЬ документ;
слияние по имени — дело импорта, где у входящего материала здесь нет истории.

Что сборщик получил — это ПОРЯДОК. Поиск по подписи теперь идёт ПЕРЕД веткой
«такого id мы ещё не видели», а не после: файл, несущий свой id для вида,
который в библиотеке уже есть, показывает на наш, а не садится рядом. Это
безопасно так, как имя — нет: равные подписи значат равный вид, терять нечего.

## 2. Один материал нельзя было ни удалить, ни отредактировать

Совсем другая причина. `getMaterialDef(id)` возвращает
`MATERIALS.get(id) || MATERIALS.get('standard')`. Всем путям РИСОВАНИЯ этот
откат нужен — грань, всё ещё носящую удалённый материал, чем-то надо красить.
Редактору — нет.

Карточка в полке запоминает свой id в замыкании при сборке полки, а импорт или
откат переименовывают и выбрасывают id под открытой полкой: `restoreDoc` только
сбрасывает `_matPreviews`, но полку не пересобирает. Открытие такой карточки
отдавало ПРЕСЕТ Solid под именем мёртвой карточки: заголовок «Solid (preset)»,
кнопка Delete спрятана (пресеты не удаляются), Reset восстанавливал Solid, а все
одиннадцать ручек тихо правили Solid. Снаружи это материал, который поселился и
к которому не подступиться.

Четыре независимые части:

- **`liveMaterialDef(id)`** — строгий поиск, возвращает `null`. Используется в
  `openMatEditor`, `meApplyLive`, `meReset`, `meDelete`. `getMaterialDef`
  сохраняет откат для всего, что рисует.
- **`matTrayStale()` + пересборка внутри `refreshMatTray()`.** Карточки обязаны
  БЫТЬ библиотекой; если нет — пересобрать. Только пока `matTrayIsOpen()`, то
  есть `open && !closing`: `setMatTrayOpen(false)` оставляет `open` на один
  переход в 240 мс, и чтение класса вручную заставляло каждый тап по выделению
  платить за `renderMatPreviews()`. O(карточек) лучше, чем помнить про
  пересборку в каждом месте, которое трогает MATERIALS, — именно это и забыли.
- **`isPresetDef(d)`** = `d.preset && presetDefaults(d.id)` вместо сырого флага
  в трёх точках, решающих судьбу кнопки. `presetDefaults` использует
  `hasOwnProperty`, а не индексацию: `MATERIAL_DEFAULTS` — обычный литерал,
  поэтому `MATERIAL_DEFAULTS['constructor']` истинно, и запись materialLib с
  `"id": "constructor"` приезжала с `preset: true`, становясь ровно тем
  неприкасаемым материалом, который этот предикат и должен убить.
- **Отказы говорят вслух.** `meDelete` на пресете и `meReset` на обычном
  материале раньше молча делали `return`; `Object.assign(d, undefined)` не делал
  ничего, но всё равно показывал «Reset to default». Кнопка, которая ничего не
  делает, читается как сломанное приложение. Плюс `saveMaterialLibrary` читала
  `MATERIAL_DEFAULTS[d.id].color` СНАРУЖИ своего try: одна запись с флагом
  пресета и без дефолта уносила с собой всё сохранение библиотеки.

## Чему это научило

Первая версия не содержала почти ничего из правильного. Собственный зонд поймал
два дефекта (`restoreDoc` принимал чужой id, не успев спросить библиотеку;
`matTrayStale` читал закрывающуюся полку как открытую). Затем ревьюер-агент без
привязанности к коду нашёл ещё СЕМЬ, три из них уровня замысла: ключ по имени на
пути восстановления молча терял виды из сохранённого файла; слияние при импорте
не проверяло вид вообще, и золотой «Metal» становился серым; ключи прототипа
удовлетворяли проверку на пресет. Первая попытка «лечения» в
`loadMaterialLibrary` оказалась недостижимым мёртвым кодом — прогон по сломанным
сборкам доказал это тем, что его удаление не изменило ни одной проверки — и была
заменена на производный предикат.

**Вывод для следующего раза:** «слить по имени» звучит как одно правило, а
оказалось четырьмя, и три из четырёх нашлись только потому, что код читал
кто-то, кто его не писал. Свежий ревьюер на любой существенный кусок — не
формальность.

## Зонд

**`_matchk.js` / `_matchk.py`** (порт 8902), 46 проверок в трёх группах:
слияние по имени и все ограничивающие его правила, путь восстановления,
редактор. Проверен против **14** намеренно сломанных сборок
(`_mkmatbroken.py`, прогон `_matbrokenrun.py`): merge, unnamed, presettarget,
samefile, slice, namekey, harvest, protokey, strict, tray, trayopen, save,
heal, mute — каждая обязана провалить именно те проверки, которые ломает.
Поймано 14 из 14. Полный набор из 35 зондов зелёный, 34 из 35 выводов
побайтово совпадают с v2.28.

## Что открыто

Живую библиотеку пользователя увидеть не удалось: она лежит в localStorage
origin'а локального файла, куда расширение браузера не достаёт. Правка
устраняет МЕХАНИЗМ (устаревшая карточка живёт только до перезагрузки). Если
материал переживает перезагрузку v2.29 — диагноз неполон, и нужно его имя и
то, что именно происходит при попытке удалить.
